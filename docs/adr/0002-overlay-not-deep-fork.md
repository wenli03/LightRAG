# ADR 0002 · 用 overlay 与网关接入，而不是深改上游

- 状态：已接受
- 日期：2026-09-29
- 相关：ADR 0001（扩展点清单）

## 背景

上游是一个 4 万行级别的活跃项目，`main` 分支每天都有依赖升级合入。
在这个前提下，"把治理能力加进去"有两条路：

- **A. 深改上游**：改 `operate.py` 的写入函数、改 `kg_query` 的返回、改 `query_routes` 的端点。
- **B. overlay + 网关**：新增自包含的 `enterprise/` 包，通过三个公开挂载点接入；
  对外只暴露自己的网关，上游服务端不直接对公网开放。

## 决策

选 **B**。具体接入方式与理由：

| 能力 | 挂载点 | 为什么这个挂载点是最小改动 |
| --- | --- | --- |
| 图谱写入护栏 | 包装 `rag.chunk_entity_relation_graph` | 上游在 `__post_init__`（`lightrag.py:1868`）建好存储，之后所有读写都经该属性，**含 rebuild 路径**；套代理即全覆盖 |
| 记账与降级 | 替换 `llm_model_func` | 它就是一个普通可调用对象（`lightrag.py:995`），上游只按 `prompt / system_prompt / history_messages` 调用（`operate.py:4907`） |
| 只取上下文不生成 | `QueryParam.only_need_context` | 上游原生支持（`base.py:102`），无需改查询逻辑 |
| 证据门槛与引用强制 | 自有网关的响应后处理 | 证据包里已带 `chunks` 与 `references`（`utils.py:7722-7732`），不需要额外查询 |
| 公网暴露面 | 自有网关的鉴权/限流/预算 | 上游鉴权是 FastAPI 依赖而非中间件（`utils_api.py:392`），从外面拦比自己重排依赖链更稳 |

**唯一真正改到上游文件的，是启动自检这一处**（`enforce_exposure`）：
它拦的是上游默认白名单把 `/api/*`（Ollama 兼容路由）放行这个安全问题——
这属于可以提回上游的修复，而不是我们私有的定制。

## 代价与收益

**代价**：

1. 上游的 WebUI 不再直接对外可用，需要在网关里单独挂载演示界面；
2. 多一跳 HTTP/函数调用；
3. 上游若把存储初始化挪出 `__post_init__`，`install_graph_guard` 会失败——
   我们让它在失败时**明确报错并指向本 ADR**，而不是静默降级成"没有护栏"。

**收益**：

1. **rebase 不痛**：上游每天的依赖升级不会与我们的改动冲突；
2. **diff 可逐行讲**：`git diff upstream/main` 里"哪些是上游、哪些是我们的"一目了然；
3. **护栏可单独测试**：`enterprise/` 不 import 上游，所以整套护栏测试在零依赖环境里可跑，
   意味着"护栏有没有真的拦住"是可证伪的（进入 CI 门禁的前提）；
4. 这恰好也是企业里最常见的集成形态：**不动别人的核心，在自己这一侧把不变量守住**。

## 被否掉的方案

**深改上游 `operate.py` 的写入函数**：否决理由有两条。
其一，rebuild 路径绕过了 `merge_nodes_and_edges`（`operate.py:1817/2286/2337`），
只改合并函数会漏；要覆盖全就得改三处以上，改动面立刻放大。
其二，把校验写进别人的热路径之后，上游每次重构我们都要跟着改，
而**维护成本会在我们看不到的地方复利**。

**只做一个"外壳 README"式的二开**（fork 之后只加文档不提功能）：不构成可验证的二开，
面试官一问"你改了什么"就没话说。
