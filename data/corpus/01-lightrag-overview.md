# LightRAG 的定位、存储分层与查询模式

## 它是什么

LightRAG 是一个把"检索增强生成"做成**图结构**的开源框架：它不只是把文档切成块存进向量库，
还会用大模型从文本里抽取实体与关系，构建一张知识图谱，回答时同时走图谱多跳与原文片段两条路。
它由香港大学数据科学实验室（HKUDS）开源，采用 MIT 许可。

它与向量 RAG 的分工可以这样理解：**向量 RAG 解决"这段文字像不像"，
图 RAG 额外解决"这件事和那件事之间是什么关系"**。前者擅长找相似段落，
后者擅长回答"甲和乙之间隔着几步"这类需要把多条事实串起来的问题。

## 四类存储与默认配置

LightRAG 把状态拆成四类存储，默认全部是**进程内存 + 本地文件持久化**，不需要任何外部服务：

- **键值存储**：保存全量实体、全量关系、文本切片等原始数据，默认实现是把内容写成 JSON 文件。
- **向量存储**：保存实体、关系与原文切片的向量，默认实现是一个轻量的本地向量库文件。
- **图存储**：保存实体节点与关系边，默认实现基于 NetworkX，落盘为图文件。
- **文档状态存储**：记录每个文档处于"待处理 / 处理中 / 已完成"的哪个阶段。

需要强调的是：**默认存储只适合小规模测试、评测与调试**。因为整个数据集常驻服务进程内存，
工作目录下的文件只是持久化副本，容量上限实际由**可用内存**决定。要上生产，
官方推荐替换成 PostgreSQL（一个库承载四类存储）、MongoDB 或 OpenSearch，
向量与图也可以分别换成 Milvus、Qdrant、Neo4j、Memgraph 等专用后端。

## 查询模式

查询模式决定了"回答时去看哪些证据"，LightRAG 提供五种：

- **local**：以命中的实体为起点，看这些实体周边的邻居关系，适合问具体对象。
- **global**：面向关系与主题层面做聚合，适合问"整体上这件事怎么分类"。
- **hybrid**：local 与 global 混合。
- **naive**：退化成最朴素的向量检索，只看原文切片，不看图谱。
- **mix**：默认模式。它在 hybrid 的基础上**额外把原文切片也纳入上下文**，
  也就是"图谱里的关系"和"库里的原话"同时看。

`mix` 之所以是默认，是因为纯图谱答案缺少逐字可引用的原文，而纯向量检索又拿不到多跳关系。
代价是上下文更长、token 更贵，因此实际使用中往往需要按问题类型分流。

## 服务端与界面

LightRAG 自带一个服务端，对外暴露完整的 REST 接口，并内置两套前端入口：
一个是**管理控制台**，可以上传文档、浏览知识图谱、带着查询参数面板做调试；
另一个是**纯查询入口**，只有一个对话界面，面向移动端或对外分享。

这里有一条容易被忽略的安全事实：服务端的 Ollama 兼容路由（路径以 `/api/` 开头）
**默认是开放的**，而默认的白名单配置也把 `/api/` 排除在鉴权之外。
也就是说，按默认配置把服务绑定到对外地址，等于把模型额度公开出去。
官方文档对此有明确提示：暴露到网络之前必须配置访问密钥，或者把监听地址限制在回环地址。
